| `scripts/push_via_api.py` | git push 报 502 时的兜底：用 Git Data API 复刻快进式 push |

### 关键设计决策与踩坑

- **索引即事实**：脚本用 `git ls-files -s` 读索引 + `git cat-file blob <sha>` 读内容，而非直接读磁盘文件。
  这样换行符规范化行为与 `git push` 完全一致，规避 Windows 下 LF→CRLF 警告带来的差异。
- **对比方式**：用 API 拉远程 tree（`?recursive=1`）与本地索引的 (mode, blob_sha) 逐条比对，
  而不是依赖本地 `origin/main` 引用——因为该引用本身可能卡在旧值（见下）。
- **删除项**：tree entry 的 `sha` 置 `null` 即可删除。
- **ref 更新用 `force=false`**，保证快进，避免覆盖他人提交；失败则让用户重跑（会基于新 HEAD 重建）。
- **本地对齐**：API commit 与本地 commit SHA 不同属预期，脚本自动 `reset --hard` 对齐并提供 `--no-sync` 逃逸。
- 已知环境事实：`gh` CLI **未安装**，凭据在 Windows 凭据管理器（username=tuoqi-stats），
  `git credential fill` 可取到。设计时不要依赖 gh。
- 本仓库 `.workbuddy/memory/` 与 `.workbuddy/skills/` **是 git 跟踪的**共享产物，正常提交，不当作本地缓存忽略。

## 用 github-push skill 完成首次真实推送（skill 自举）

按 skill 流程走完一遍，`git push` 如期报 502，改用 API 兜底成功：

| 提交 | SHA | 内容 |
|------|-----|------|
| c57c45d → 远程 2ca35d4 | `2ca35d43` | 新增 github-push skill + 更新 memory（5 文件） |
| 31a5d85 → 远程 41b2829 | `41b282930c` | skill 自身的改进（3 文件） |

远程最终 HEAD：`41b282930cded9bbe8ea62710cf49d8a0501a404`，本地与 origin/main 完全同步。

### 实战暴露并已修复的两个缺口

1. **受限网络下无法对齐本地 HEAD**：原脚本只有 `git fetch` 一条路，fetch 报 502 时拿不到 API 新建的 commit 对象，
   只能跳过对齐，导致本地 `[ahead 1]`。
   **解法（重要发现）**：带具体 SHA 的 fetch 走的是**不同通道**，在普通 `git fetch` / `git push` 均 502 时仍然成功：
   ```bash
   git fetch --no-tags https://github.com/<owner>/<repo>.git <具体SHA>
   ```
   原因：普通 fetch 走 git smart-http 端点（被拦），按 SHA 取对象走的是另一条路。
   已封装为 `materialize_remote_commit()`，实测第二次推送即自动对齐成功。

2. **`git update-ref` 修复跟踪引用会静默失效**：引用困在 packed-refs 时，`git update-ref refs/remotes/origin/main <SHA>`
   **返回 0 但不生效**（本次实测：执行后仍是旧值 95ebc83）。
   必须用 `git rev-parse` 复核，失效时降级为直接写 loose ref。
   已在 `sync_local()` 中加复核 + 降级 + 最终复核三步。
