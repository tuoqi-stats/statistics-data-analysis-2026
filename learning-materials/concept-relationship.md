# 概念关系：Agent、上下文与 Skill（Concept Relationship）

> 生成日期：2026-09-09 ｜ 类别：AI 概念学习资料

（注：本文串联本库已有的三个概念——[Agent Skill（智能体技能）](agent-skill.md)、[大模型上下文](llm-context.md)、[Skill（技能）](skill.md)——阐述三者在当代智能体系统中的三角协作关系，而非单独解释任一概念。三篇单概念文档讲"各自是什么"，本文讲"它们怎么咬合在一起"。）

## 1. 概念个人解释

先打个比方：你要装修一间房子。

- **Agent** 是那位装修师傅——有力气、会用电钻、能看图纸，但没进过你家，不知道你家的线路怎么走、墙面用哪种漆。
- **上下文（Context）** 是师傅面前那张工作台——台面尺寸有限，你把图纸、色卡、物业规定一张张往上摆，摆不下就得收起一些旧的。
- **Skill（技能）** 是书架上的一排操作手册——"贴砖流程""刷漆规范""水电验收清单"。师傅不会时刻把所有手册摊在台面上，而是需要哪本翻哪本，翻完搁回架子上。

三者的关系就是：**师傅（Agent）站在工作台（Context）前干活，遇到不熟的工序就从书架（Skill）上取一本手册摊到台面上照着做。** 工作台太小塞不下所有手册，所以取用讲究时机——这就是三角关系的核心张力。

正式一点说：Agent 是基于大模型的自主推理与执行引擎，以"感知—推理—行动"循环驱动任务；上下文是 Agent 每次推理时可见的有限信息窗口，是 Agent 与外界交互的唯一通道；Skill 是外化为文件的可加载程序性知识，平时零成本静默于磁盘，任务匹配时被加载进上下文，赋予 Agent 特定领域的操作能力。三者构成"能力 = 基座模型 × 上下文管理 × 技能注入"的乘法关系——缺任何一项，系统要么能干但不知道干什么（无技能），要么有知识但无法行动（无 Agent），要么行动却看不见信息（无上下文）。

## 2. 核心机制或组成

三角关系通过以下四条机制咬合运转：

1. **加载链：Skill → Context → Agent**
   技能平时是磁盘上的静态文件（零上下文成本）；任务到来时，Agent 依据技能的触发描述（description）判断是否需要加载；匹配后，SKILL.md 全文被读入上下文；Agent 随后依据上下文中的指令执行。这是一条单向流水：技能不主动行动，上下文不自行思考，Agent 不预知未加载的内容。

2. **上下文作为唯一交汇面**
   三者中，只有上下文是 Agent、Skill、外部信息同时"在场"的地方。Agent 只能作用于上下文中的信息；Skill 只有被加载进上下文才能发挥效用；工具返回的结果、RAG 检索的片段也必须拼入上下文才能被 Agent 感知。上下文窗口的大小，因此成为整个系统的共享瓶颈——它同时约束了"能记住多少对话""能装多少技能""能引用多少资料"。

3. **渐进式披露——三角关系的节流阀**
   这是让三者协同可扩展的关键设计（详见 [agent-skill.md](agent-skill.md) 第 2 部分）：
   - 启动：Agent 只加载所有技能的名称与一句话简介（每个约几十 token）→ 上下文几乎无负担
   - 匹配：任务命中某技能时，才读入该技能 SKILL.md 全文（几千 token）→ 定向加载
   - 深入：执行中需要细节时，才读 references/ 附录（可上万 token）→ 按需取用

   本质上，渐进式披露就是上下文工程（Context Engineering，见 [llm-context.md](llm-context.md) 第 2 部分）在技能管理上的具体应用——用"分层加载"换"窗口不被技能挤爆"。

4. **两类知识、一个窗口的张力**

   | | 内隐知识（权重内） | 外显知识（Skill，权重外） |
   |---|---|---|
   | 在场方式 | 始终可用，不占上下文 | 必须加载进上下文才生效 |
   | 修改成本 | 重新训练（百万美元级） | 编辑文件（分钟级） |
   | 与 Agent 的关系 | Agent"天生会" | Agent"读了才会" |
   | 与 Context 的关系 | 零窗口开销 | 按加载量计 token |

   张力在于：技能越多，Agent 的能力面越广，但上下文管理的压力也越大——这恰恰是渐进式披露存在的理由。

## 3. 具体应用场景

1. **WorkBuddy + concept-material-generator（你正在体验的系统）**：用户说"生成 XX 概念的学习资料"→ WorkBuddy（Agent）在上下文中持有数十个技能的名称简介，匹配到 concept-material-generator → 将其 SKILL.md 全文加载进上下文 → 按指令执行查重、撰写五部分、自检、保存。此刻你读的这篇文档，正是三角关系的一次完整运转产物：Agent 依 Skill 指令、在 Context 内完成推理与文件写入。

2. **Claude Code 长时编程任务**：编程 Agent 将代码库地图、会话历史拼入上下文（Context 工程——接近上限时自动压缩摘要）；同时按子任务加载团队规范技能（提交格式、部署流程）（Skill 渐进披露）；在数小时的多步任务中，三者持续协同——上下文管理保住"记忆"，技能注入保住"规范"，Agent 推理保住"决策"。Anthropic 的上下文工程博客与 Agent Skills 发布正是同一架构的两块拼图。

3. **Claude.ai 自定义技能 + 长文档分析**：用户上传品牌规范作为自定义技能（Skill），在 200K 窗口（Context）内同时放入长文档全文与技能指令，Agent（Claude）据此生成符合品牌调性的文案。大窗口降低了"塞不下"的紧迫性，但技能的按需加载仍让窗口保持精简——大窗口与技能不是替代关系，而是"保险 + 效率"的双重保障。

4. **多技能协作场景**：一个 Agent 同时持有 Excel 分析、图表生成、报告写作三个技能。任务"分析数据并出报告"到来时，Agent 先加载 Excel 技能处理数据 → 完成后卸载、加载图表技能生成可视化 → 再切换到写作技能输出报告。上下文在不同技能间轮转，渐进式披露确保每次只在窗口中放"当前需要的知识"——这是三角关系在复杂工作流中的动态形态。

## 4. 容易混淆的问题或使用边界

1. **Agent vs Skill——谁在干活？**
   Agent 是执行者（推理、决策、调用工具）；Skill 是说明书（做什么、按什么顺序、什么风格）。没有 Agent 的技能只是一份文档，没有技能的 Agent 能力强但缺乏领域规范。类比：外科医生（Agent）+ 手术流程手册（Skill）——医生的手艺在脑子里，手册在手上，二者缺一不可。

2. **Skill vs Context——存储与加载**
   Skill 是持久存储（磁盘文件，始终可用，休眠时零 token 成本）；Context 是工作记忆（加载后活跃，按 token 计费）。从 Skill 到 Context 的转换就是"加载事件"——渐进式披露控制的是这一事件的发生时机与加载量。一个技能可以永远存在而不被加载，但一旦加载就必然消耗上下文预算。

3. **"加技能" vs "扩窗口"——两条路线**
   扩大上下文窗口（如 200K → 1M）让人能把更多信息一股脑塞进去；增加技能让人保持窗口精简、按需加载。二者互补而非替代：大窗口降低了"塞不下"的紧迫感，但更多内容 = 更多噪声 = 更高成本（lost in the middle 现象、指令遵循率随长度下降）。行业趋势是双管齐下——窗口在变大，但上下文工程与技能渐进披露的纪律没有放松。

4. **三角关系的失效模式**：
   - **技能永不加载**（触发描述写得含糊）→ 上下文有富余但 Agent 缺能力，等于有书架但从不翻书
   - **技能过度加载**（无渐进披露，全部塞入）→ 上下文被技能挤爆，Agent 注意力分散、成本飙升
   - **上下文失管**（长任务无压缩）→ 窗口溢出，历史丢失，即便有好技能也无从附着
   - **Agent 能力不足**（基座模型不具备某项基础能力）→ 技能指令再详尽也无法注入模型不具备的能力（[skill.md](skill.md) 第 4 部分：技能是"组织能力"而非"注入能力"）
